PART 05Identity and LDAP

config/ldap.php reads every setting from environment (FastCGI Environment Variables in IIS). Defaults: LDAP_ENABLED=false, host 127.0.0.1, port 389, LDAP_DOMAIN=couriva.local, LDAP_BASE_DN=dc=couriva,dc=local, LDAP_ALLOWED_OU_DN=OU=CourivaUsers,DC=couriva,DC=local, LDAP_REQUIRE_TLS=true, LDAP_ALLOW_LOCAL_ADMIN_FALLBACK=true, LDAP_FALLBACK_LOCAL=false, LDAP_AUTO_CREATE=true.

Variable Production value Meaning
LDAP_ENABLED true enables domain auth
LDAP_HOST / LDAP_PORT DC FQDN / 636 LDAPS endpoint
LDAP_USE_SSL / LDAP_USE_TLS true / false LDAPS, not STARTTLS
LDAP_BASE_DN dc=couriva,dc=local (doc) / dc=couriva,dc=com (live) search root
LDAP_ALLOWED_OU_DN OU=CourivaUsers,... login restricted to this OU
LDAP_BIND_DN / LDAP_BIND_PASSWORD service account / secret directory search; never on disk
LDAP_REQUIRE_TLS true fail closed without TLS
LDAP_AUTO_CREATE true first login provisions mailbox
LDAP_FALLBACK_LOCAL false no local fallback for LDAP users
LDAP_ALLOW_LOCAL_ADMIN_FALLBACK true break-glass local admin only

Password rules: minimum 10 characters, uppercase, lowercase, digit, symbol. LDAP users are directed to the domain controller; Couriva never changes AD passwords. ad_object_guid is immutable and unique (migration 006), so renames cannot hijack a mailbox.

Full ERD walkthrough — Spoon-feed guide (Figures 1A to 1E / Figs. 41–45)

How to read Crow's Foot symbols in 10 seconds: a single bar (|) means ONE, a three-prong crow's foot (<) means MANY, and a circle (o) means OPTIONAL (can be NULL / 0). So |──o< means "one parent can have zero, one, or many children."

Figure 1A (Fig. 41) — Core Identity & Messaging (users, emails, folders)

Plain-English story: Everything starts with a person (users) sending or receiving a message (emails), and optionally filing it into a personal folder (folders).

  • users (1) ──< (N) emails via sender_id: One user can send many emails, but every email has one sender.
  • users (1) ──o< (N) emails via recipient_id: One user can receive many emails (recipient_id can be NULL for drafts/multi-recipient).
  • emails (1) ──o< (N) emails via parent_email_id (self-relationship): A reply points back to its parent email so Couriva builds a conversation thread in public/read.php.
  • folders (1) ──o< (N) emails via custom_folder_id (ON DELETE SET NULL): One custom folder can hold many emails; deleting the folder keeps the emails safe and just clears custom_folder_id.
  • users (1) ──o< (N) users via reviewed_by: Records which admin reviewed a user account.

If a panelist points at Fig. 1A, say: "Figure 1A is the core mailbox backbone: users stores Active Directory-linked accounts (ad_object_guid, auth_source), and emails links senders, recipients, custom folders, and self-referencing parent_email_id threads."

Figure 1B (Fig. 42) — Recipients & Attachments (email_recipients, attachments)

Plain-English story: One email can go to multiple people (To, Cc, Bcc) and carry multiple files—so we store them in child tables instead of squeezing lists into one column.

  • emails (1) ──< (N) email_recipients (ON DELETE CASCADE): One email has one or more normalized recipient rows (recipient_type = to, cc, or bcc). Deleting the email deletes its recipient rows automatically.
  • users (1) ──o< (N) email_recipients (ON DELETE SET NULL): Links to the recipient's user row if they exist, while always keeping email_address as a permanent text snapshot.
  • emails (1) ──< (N) attachments (ON DELETE CASCADE): One email can have many uploaded files. Each row stores the user's original_filename, randomized stored_filename, mime_type, and byte size; the file bytes live safely in non-executable storage/attachments/.

If a panelist points at Fig. 1B, say: "Figure 1B normalizes multi-recipient To/Cc/Bcc addressing and file attachments into 1-to-many child tables with cascading deletes when a message is permanently purged."

Figure 1C (Fig. 43) — Mailbox Organization & Contacts (folders, labels, email_labels, contacts)

Plain-English story: Each user organizes their own mailbox privately—custom folders, color labels, and personal contacts belong strictly to one user_id.

  • users (1) ──< (N) folders & users (1) ──< (N) labels & users (1) ──< (N) contacts (all ON DELETE CASCADE): One user owns many folders, many color-coded labels, and many personal contacts. No user can ever see another user's folders or contacts.
  • emails (M) ──< email_labels >── (N) labels (Many-to-Many bridge table): One email can have multiple labels (e.g., Urgent + Project), and one label can tag many emails. email_labels resolves this M:N relationship using a composite key (email_id, label_id).

If a panelist points at Fig. 1C, say: "Figure 1C models per-user mailbox organization: folders, labels, and contacts are 1-to-many from users, while email_labels is the many-to-many junction table between emails and labels."

Figure 1D (Fig. 44) — Scheduled Dispatch, Delivery & Notifications (scheduled_emails, delivery_status, notifications)

Plain-English story: When a user clicks Schedule, the message waits safely in a queue until Task Scheduler runs bin/process_scheduled.php every minute, tracks delivery, and alerts the recipient.

  • users (1) ──< (N) scheduled_emails: One user can queue many future-dated emails.
  • emails (1) ──< (N) scheduled_emails via draft_email_id and sent_email_id: Links the queued job to the draft before sending, and to the final sent email afterward. Status moves atomically scheduled → processing → sent so two worker runs can never double-send.
  • emails (1) ──< (N) delivery_status (ON DELETE CASCADE): Tracks per-recipient delivery state (queued, delivered, sent, failed, bounced), idempotency key, and retry count.
  • users (1) ──< (N) notifications (ON DELETE CASCADE): Stores unread/read in-app alerts when new mail arrives.

If a panelist points at Fig. 1D, say: "Figure 1D powers reliable background sending: scheduled_emails locks due drafts for the 1-minute Task Scheduler worker, delivery_status guarantees idempotency, and notifications alerts recipients."

Figure 1E (Fig. 45) — Spam Moderation, Blocking & Audit (blocked_senders, spam_reports, system_logs)

Plain-English story: Users can silently block unwanted senders or report a suspicious message to an admin—without letting the admin read the rest of their inbox—and every security action is logged.

  • users (1) ──< (N) blocked_senders (ON DELETE CASCADE): One user can block many sender addresses; future mail from them routes silently to Spam.
  • users (1) ──< (N) spam_reports (as reporter_id and admin reviewer_id) & emails (1) ──< (N) spam_reports (ON DELETE CASCADE): Ties a report to only one specific email_id so admin/spam-reports.php stays privacy-isolated.
  • users (1) ──o< (N) system_logs (ON DELETE SET NULL): Immutable audit trail of logins, failed auth, password changes, and admin governance actions.

If a panelist points at Fig. 1E, say: "Figure 1E handles safety and accountability: blocked_senders enforces per-user blocks, spam_reports exposes only the single reported email_id to admins, and system_logs records all security events."

6.3 Schema and migrations

database/schema.sql is the canonical DDL (no USE, safe for disposable DBs). Migration ledger:

File Purpose
001_p1_security.sql must_change_password, session_epoch, sender snapshots, ON DELETE SET NULL
002_couriva_features.sql approval states, folders, labels, archive/snooze, scheduled mail, notifications, blocks, spam reports
003_couriva_domain.sql @webmail.local → @couriva.local rewrite (idempotent)
004_delivery_status.sql durable per-recipient delivery state + idempotency
005_ad_auth_source.sql auth_source ENUM('local','ldap')
006_ad_object_guid.sql immutable ad_object_guid unique binding

Fresh installs import schema.sql only; upgrades apply migrations 001–006 in order after backup.
